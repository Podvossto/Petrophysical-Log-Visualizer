# DATA_NOTES — what the real files look like and the rule each finding led to

How to read this file: every finding has **Observed** (a fact with a file name and line number you can open), **Rule** (a general rule — taken from the LAS 2.0 spec or from the evidence, never from one sample file) and **Test** (what must be tested later). Numbers come from a real scan of all 203 files in `data/` (the scan script is a throwaway tool and is not part of the product). Findings are numbered D-01 to D-21 in six groups: files, header, data, depth, missing-value markers, curves and units.

Scan limits: the scan only counts and looks; it changes nothing. It reads the data section as plain text tokens, so it cannot tell *why* a value is odd — that is what the findings below explain. The first scan had a bug (it treated LAS 3.0 lithology/comment sections as data); it was fixed and everything here comes from the corrected run.

## Glossary (values you will see in a LAS file)
| Term | Meaning | Example |
|---|---|---|
| `~V ~W ~C ~P ~A` | Sections: version, well info, curve definitions, parameters, data (ASCII) | `~A` starts the numbers |
| `MNEM.UNIT  VALUE : DESCRIPTION` | One header line; mnemonic is everything before the first `.` | `STRT.FT  2000.0 : First depth` |
| STRT / STOP / STEP | First depth, last depth, spacing between rows (may be wrong or 0) | `STEP.FT 0.5` |
| NULL | The number this file uses for "no measurement" | `NULL. -999.25` |
| WRAP | `NO` = one depth row per line; `YES` = a row is spread over several lines | `WRAP. YES` |
| Curve | One measured column (the first column is depth) | GR, RHOB, NPHI |
| GR / RHOB / NPHI / resistivity | Gamma ray (API) / bulk density (g/cc) / neutron porosity (v/v or %) / how strongly rock resists current (ohm.m, plotted on a log scale) | — |
| Sentinel | A fake value standing in for "missing", such as -999.25 or -9999 | — |

## 1. Files and encoding
**D-01 File extension case.** Observed: 170 files end `.las`, 33 end `.LAS`. Rule: discover files case-insensitively. Test: folder with both spellings loads both.

**D-02 Line endings and encoding.** Observed: 199 files use CRLF, 4 use LF only, 0 mix them; 0 have a BOM; 17 contain bytes above 127 (non-ASCII text in headers); 1 contains NUL bytes. Rule: split lines on `\n` and trim `\r`; read the file as single-byte text (Latin-1) so no byte is lost and non-ASCII header text never throws — the numbers are plain ASCII anyway. Test: CRLF and LF strings give the same result; a non-ASCII byte in the header does not fail the load.

## 2. Header
**D-03 Version and WRAP are written in different forms.** Observed: VERS is `2.0` (81), `2.00` (59), `1.2` (52), `3.0` (10), `3.00` (1); WRAP is `NO` (179), `No` (10), `YES` (14). Rule: parse VERS as a number and WRAP case-insensitively; 1.2 and 2.0 are read the same way, 3.0 is best-effort (D-09). Test: `2.0`, `2.00`, `No`, `NO`, `yes`.

**D-04 NULL is written in many forms, and sometimes it is 0.** Observed (12 different spellings): `-999.25` (104), `-999.2500` (49), `-999.250` (37), `0.000` (3), `-999.20` (2), `-9999` (2), and one each of `-999.0000`, `-999999.0000`, `-999999`, `0`, `0.0000`, `-.9999`. So 5 files declare NULL as zero (example: `4238336177MAIN.las`). Rule: parse NULL as a number, compare as numbers (not text). A declared NULL of 0 is **not** applied — zero is a real reading for many curves — and the report gets a warning. Whether such files also use another sentinel in the data is checked in part 2. Test: `-999.2500` equals `-999.25`; NULL 0 leaves zeros untouched and adds a warning.

**D-05 Header lines are not always tidy.** Observed: `4246135297Repeat.las` line 51 is `Bit IN.e   : MM` inside the curve block — the mnemonic contains a space, and a strict "no spaces" pattern skipped it, so the header seemed to have 23 curves while every data row has 24 values. Rule: split a header line at the first `.` (mnemonic = text before it, may contain spaces) and at the last `:` for the description; never drop a line from the curve block silently — count curves from the block, then compare with the data columns and report a mismatch. Test: a mnemonic with a space is still counted as a curve.

## 3. Data section
**D-06 A lone Ctrl-Z (0x1A) line at the end.** Observed: 7 files, for example `4200341369_DEVON_ULS_5_35_1_MainPass.las` line 90450 is a single character 0x1A (DOS end-of-file marker). Rule: a data line consisting only of 0x1A is the end of the data — stop there, add an info entry; it is not a value and not a row. Test: data followed by 0x1A gives the same rows as without it.

**D-07 Text that stands in for a number.** Observed: `1.#INF` (`4200342764_UNIV_42_1_ECS_Playback.las` line 9575), `-1.#IND` (`4238338546_University_2505_3HM_.las`, lines 3481 and 6028 among others), `(null)` ×167 (`4246137956_UNIV_NG_5021H_5INCH_HORIZONTAL.las`, line 126), `********` (Fortran overflow, `4200340740PnrUniv7-23_1.las` lines 4970 and 5253). Rule: a token that is not a number becomes `NaN`, counted per file and per curve in the report — the row stays and the other curves keep their values. Test: each of these four tokens in a row gives `NaN` for that cell only.

**D-08 Damaged line.** Observed: `4200340740PnrUniv7-23_1.las` line 10508 is a run of NUL bytes (with a 0x1A inside) instead of a data row; the scan counted it as one token. Rule: a line that cannot be split into the expected number of numeric values is reported with its line number; it is not turned into a row of invented values. Whether to skip such a line or turn it into an all-NaN row is decided with the depth rule in part 2 (an all-NaN row has no depth). Test: a line of NULs in the middle of data does not stop the load and is reported.

**D-09 Rows with the wrong number of values.** Observed: `4246135949_MAIN.las` has 17307 rows of 29 values and 3054 rows of 28, starting at line 8247 (the last value of the row is missing); `4200340123MAIN.las` ends with one row of 12 values (23 expected). Also 6 files have more values per row than curves in the header (24 vs 23, 34 vs 33, 20 vs 19, 88 vs 82, 39 vs 37) — the cause is not proven for each (D-05 explains the first). Rule: a row with fewer values than curves keeps its depth and the missing curves become `NaN`, with a warning that gives the line number and counts — the file is not rejected; a row with more values than curves is reported, and the extra values are not used. Proposed, to be confirmed by the owner. Test: short row → trailing `NaN`; long row → warning.

**D-10 WRAP = YES.** Observed: `4200340125Univ_7_8_1.LAS` (25 curves) writes the depth alone on one line, then lines of 6 values (1, 6, 6, 6, 6 values). The biggest wrapped file, `4200345990_20140426_LAS(masmp).LAS`, declares 123 curves but its lines add up to a different count per row (not yet explained — to check in part 2). Rule: when WRAP is YES, read values until one row has as many values as there are curves, then start the next row; never assume a fixed number of values per line. Test: wrapped sample gives the same table as the unwrapped version of the same data.

**D-11 LAS 3.0 and repeated sections.** Observed: the 11 LAS 3.0 files have extra sections after the data (`~Lithology_Data`, `~Comment_Definition`, `~TracePresentation…`); `s_1e95aa3fbeb17f98a969ce83d5962c1c.las` has `~Parameter`, `~Curve` and `~Ascii` twice. Rule (scope says 3.0 is best-effort): read the first `~A…` or `~Log_Data` section only, ignore sections that do not start the data, and add an info entry that other sections were skipped. Test: a 3.0 sample with a lithology section still loads its log data.

**D-12 The header can lie about WRAP.** Observed: `4200340122MAINCOR.las` says `WRAP. NO` but its 26 curves are spread over 6 lines per row (line shapes: 6 values ×82580 lines and 1 value ×41290 lines). Its first rows at lines 175–181 show a depth, then lines starting with `-999.25`. Rule: decide the layout from the data, not only from the header: count the values on each line of the first rows; if the lines hold fewer values than curves, read as wrapped (a stream of values, `ncurves` per row) and add a warning that the header disagrees. Test: wrapped data with `WRAP. NO` still gives complete rows.

## 4. Depth
**D-13 Depth units are all feet, written four ways.** Observed: the first curve is `DEPT` or `DEPTH`/`Depth`, with unit `F` (88 files), `FT` (86+5), `ft` (7+5+2) or `Ft` (10); the STRT/STOP/STEP lines use the same four spellings. No file labels its depth as metres. Rule: depth is the first column; compare its unit case-insensitively; `F`, `FT` = feet; a metres label (`M`) would be converted to feet with a report entry — there is no such file here, so this rule comes from the spec only and gets a small test. Test: `F`, `FT`, `ft`, `Ft` all mean feet; `M` converts.

**D-14 Depth order.** Observed (non-wrapped files, from the scan): 161 ascending, 25 descending (example `4246135332_repeattwo.las`), 3 neither; 14 wrapped files were not checked. Two of the three "neither" are real: `4200343170_STATE_AQ_8_RUN2.las` jumps back at line 4464 (7763.5 → 7664.0) and then runs downwards from about line 8614; `s_1e95aa3fbeb17f98a969ce83d5962c1c.las` drops at line 20510 (10194.0 → 24.5) where its second `~Ascii` section starts (D-11). The third, `MAINCOR`, only looks mixed because it is wrapped (D-12). Duplicate depths and the 518 count seen in `MAINCOR` are therefore not trustworthy yet — recount after the reader handles wrap. Rule: all descending → reverse the rows as a block; otherwise (jumps) → stable sort by depth, never reorder values inside a row, report how many rows moved; duplicates: first kept, counted (F3). Test: descending, jump-back and duplicate samples.

**D-15 STEP in the header is not reliable.** Observed: header STEP and the most common real step were compared in 189 files and differ in 3 (`4200340125MAIN.las` header 0.75, real 0.5; `4200342472_UNIV_9_31_1_LAS.las` header 0.25, real 0.5; the third is MAINCOR, an artifact). Rule: report both; use the real step for gap detection; never resample (scope). Test: a file whose STEP is wrong reports both numbers.

## 5. Missing-value markers
**D-16 Files use other markers besides the declared NULL.** Observed: `-9999.9999` appears in 11 files whose NULL is `-999.25` (1836 values in `s_7eec8ccf38a0378c41a61b611c4bf6d6.las`); `-999.0000` in 4 files declared `-999.25`/`-999.2500` (7902 values in `4200341177_DRONE_BEE_1_MSIP_UBI_SP…las`); `4238336177MAIN.las` declares NULL `0.000` but contains `-999.250` 11840 times. Values such as `-270.1804` repeat only 3 times in one file, so they are real readings: "any value below -90" is **not** a valid rule. Rule (proposed — the sentinel list is the owner's call): always apply the declared NULL (except 0, D-04) **and** a short fixed list of known markers `-999.25, -999, -9999, -99999, -9999.9999`, matched as numbers; the report counts each marker per curve. Test: each marker → `NaN`; a normal value near -270 stays.

## 6. Curves and units
Method: each curve was found by mnemonic, then its values were looked at (non-wrapped files with consistent rows, markers excluded) to see what the unit label really means. "Median" below = median over curves of each curve's own median.

**D-17 Neutron porosity: the unit label is not enough, and the old assumption was wrong.** Observed: `NPHI`, `TNPH` and `NPOR` are labelled `CFCF` on 124 curves (median 0.159, none with a median above 1) — these are fractions, not counts. `PERC` (49 curves, median 18.6), `PU` (8, 13.5) and `%` (5, 15.0) are percent. `V/V` (33, 0.161), `FRAC` (6, 0.226) and `DECP` (7, 0.265) are fractions. `CNLSC` with unit `CPS` (10 curves, median 333) is a count rate, **not** porosity. Rule: choose the neutron-porosity curve by mnemonic **and** unit class — percent (`PERC`, `PU`, `%`) → divide by 100; fraction (`V/V`, `FRAC`, `DECP`, `CFCF`) → keep; counts (`CPS`) → never chosen. As a safety net, warn when a "fraction" curve has a median above 1. Proposed; the `CFCF` decision rests on the values above, so confirm. Test: 25 % → 0.25; `CFCF` curve of 0.18 kept; `CPS` curve ignored.

**D-18 Bulk density.** Observed: units are `G/C3` (78), `G/CC` (10), `G/CM3` (2), `K/M3` (1 file); mnemonics are `RHOZ` (45 files), `RHO8` (32), `DEN` (26), `RHOB` (19). `DPHI` also matches "density" names but is a porosity — it must not be a density alias. Rule: aliases live in `CurveRules.cs`; the three g/cc spellings are equal, `K/M3` is divided by 1000 with a report entry. Test: each unit; `DPHI` is not chosen as RHOB.

**D-19 Gamma ray.** Observed: `GR` (100 files), `GR_EDTC` (43), `HGR` (42), `GRGC` (29), `GRAN` (19), `GRSG` (17), `GAMMA` (17); unit `GAPI` (131 curves), `API` (8). Rule: all of these units mean the same; when a well has several gamma candidates, take the first in the alias priority order and list the others in the report (F5). Test: two candidates → one chosen, the other reported.

**D-20 Resistivity.** Observed: many names — `RT_HRLT` (40 files), `DSLL`/`DDLL` (30 each), `LLD`/`LLS` (8), `RILD` (6), `MSFL` (6); unit `OHMM`, but also `OHM-M` (5 curves among the names listed) and an empty unit (`RLLD`, `RLLS`). Rule: `OHMM` and `OHM-M` are equal; an empty unit is accepted with a report entry; the deep curve is preferred over shallow/micro curves in the alias order. Test: `OHM-M` accepted, empty unit accepted with a note.

**D-21 Out-of-scale values exist in real data.** Observed (excluding markers): density from -60.112 (`G/CC`) to 4.629 (`G/C3`), gamma ray up to 711.95, neutron `PERC` up to 524, neutron `V/V` up to 1.79. Rule: these values are never changed or removed (no silent edits); the plot uses fixed standard scales and lets off-scale values run off the track; markers are a later feature (F10). Test: a density of -60 stays in the data and the plot call does not throw.
