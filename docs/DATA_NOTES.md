# DATA_NOTES — what the real files look like and the rule each finding led to

How to read this file: every finding has **Observed** (a fact with a file name and line number you can open), **Rule** (a general rule — taken from the LAS 2.0 spec or from the evidence, never from one sample file) and **Test** (what must be tested later). Numbers come from a real scan of all 203 files in `data/` (the scan script is a throwaway tool and is not part of the product). Findings are numbered D-01 to D-24 in six groups (D-22, D-23 and D-24 were added later and sit in groups 3, 6 and 1): files, header, data, depth, missing-value markers, curves and units.

Scan limits: the scan only counts and looks; it changes nothing. It reads the data section as plain text tokens, so it cannot tell *why* a value is odd — that is what the findings below explain. The first scan had a bug (it treated LAS 3.0 lithology/comment sections as data); it was fixed and everything here comes from the corrected run.

## Glossary (values you will see in a LAS file)
| Term | Meaning | Example |
|---|---|---|
| `~V ~W ~C ~P ~A` | Sections: version, well info, curve definitions, parameters, data (ASCII) | `~A` starts the numbers |
| `MNEM.UNIT  VALUE : DESCRIPTION` | One header line; mnemonic is everything before the first `.` | `STRT.FT  2000.0 : First depth` |
| STRT / STOP / STEP | First depth, last depth, spacing between rows (may be wrong or 0) | `STEP.FT 0.5` |
| NULL | The number this file uses for "no measurement" | `NULL. -999.25` |
| WRAP | `NO` = one depth row per line; `YES` = a row is spread over several lines | `WRAP. YES` |
| Curve | One measured column (the first column is depth) | GR, RHOB, NPHI |
| GR / RHOB / NPHI / resistivity | Gamma ray (API) / bulk density (g/cc) / neutron porosity (v/v or %) / how strongly rock resists current (ohm.m, plotted on a log scale) | — |
| Sentinel | A fake value standing in for "missing", such as -999.25 or -9999 | — |

## 1. Files and encoding
**D-01 File extension case.** Observed: 170 files end `.las`, 33 end `.LAS`. Rule: discover files case-insensitively. Test: folder with both spellings loads both.

**D-02 Line endings and encoding.** Observed: 199 files use CRLF, 4 use LF only, 0 mix them; 0 have a BOM; 17 contain bytes above 127 (non-ASCII text in headers); 1 contains NUL bytes. Rule: split lines on `\n` and trim `\r`; read the file as single-byte text (Latin-1) so no byte is lost and non-ASCII header text never throws — the numbers are plain ASCII anyway. Test: CRLF and LF strings give the same result; a non-ASCII byte in the header does not fail the load.

**D-24 Some files are byte-for-byte copies of another file.** Observed (SHA-256 of all 203 files, then the batch run on the code with the rule): 11 groups of two files have exactly the same bytes, so 22 files hold 11 different logs and `data/` has 192 different files, not 203. The copies differ from the original only in the name: an underscore moved (`4238336177MAIN.las` and `4238336177_MAIN.las`, 2.74 MB; two `4238336177UNIVERSITY 10-3 No 2` files; `4246135952AQZO-00038_...` and `4246135952_AQZO-00038_...`, 11.8 MB), a suffix such as `_2` or `(2)` (`4200342472_UNIV_9_31_1_MAIN.las` and `..._MAIN_2.las`, two `4200346370_20150224_...` files), or another well name for the same data (`4200340125PnrUniv7-8_1.LAS` and `..._MDL.LAS`, `4200340686_ChkUniv5-26_1.LAS` and `..._SLI8892.LAS`, `4231735947_University 6-15 # 2.LAS` and `..._UNIV_6_15_2.LAS`). Two other pairs look alike but are not copies: `4200340686_ChkUniv5-26_1_Final_LAS.las` and `..._Main_PEX-HRLA-NGT-DSI_8LUP.las` have the same size (3,407,820 bytes) and different bytes, and the two `4200346370_20150223_LAS(...ANDREWS_3001HL...)` files have names that differ only in letter case and one underscore, but different bytes. Rule: a file whose bytes are identical to an earlier file (in name order) is flagged as a copy — a line in `load-report.csv` (status WARN), a `duplicate-file` row in `conditioning-report.csv` and a line in `summary.md` ("192 files are different; 11 are byte-identical copies") — but it is still loaded, conditioned and plotted: every file is attempted (F1) and nothing is dropped without a trace. The totals in the reports therefore count a copy twice, and `summary.md` says so. Only files of the same size are hashed (the check cost 1.5 s for the 203 files by a PowerShell scan; in the program most files are never read for it); empty files are ignored. Logs that hold the same data with a different header are not detected. Result (batch run on all 203 files, Release): 11 files flagged, and in each of the 11 hash groups every file but one is flagged (checked with a separate script); the other 192 are not flagged; 203 PNG files as before. Test: three copies give two flags and the first in the list is the original; same size with different bytes is not a copy; empty and missing files do not throw (`FileDuplicatesTests`); a batch run flags a copy, still plots it and says so in the summary (`BatchRunnerTests`).

## 2. Header
**D-03 Version and WRAP are written in different forms.** Observed: VERS is `2.0` (81), `2.00` (59), `1.2` (52), `3.0` (10), `3.00` (1); WRAP is `NO` (179), `No` (10), `YES` (14). Rule: parse VERS as a number and WRAP case-insensitively; 1.2 and 2.0 are read the same way, 3.0 is best-effort (D-09). Test: `2.0`, `2.00`, `No`, `NO`, `yes`.

**D-04 NULL is written in many forms, and sometimes it is 0.** Observed (12 different spellings): `-999.25` (104), `-999.2500` (49), `-999.250` (37), `0.000` (3), `-999.20` (2), `-9999` (2), and one each of `-999.0000`, `-999999.0000`, `-999999`, `0`, `0.0000`, `-.9999`. So 5 files declare NULL as zero (example: `4238336177MAIN.las`). Rule: parse NULL as a number, compare as numbers (not text). A declared NULL of 0 is **not** applied — zero is a real reading for many curves — and the report gets a warning. Whether such files also use another sentinel in the data is checked in part 2. Test: `-999.2500` equals `-999.25`; NULL 0 leaves zeros untouched and adds a warning.

**D-05 Header lines are not always tidy.** Observed: `4246135297Repeat.las` line 51 is `Bit IN.e   : MM` inside the curve block — the mnemonic contains a space, and a strict "no spaces" pattern skipped it, so the header seemed to have 23 curves while every data row has 24 values. Rule: split a header line at the first `.` (mnemonic = text before it, may contain spaces) and at the last `:` for the description; never drop a line from the curve block silently — count curves from the block, then compare with the data columns and report a mismatch. Test: a mnemonic with a space is still counted as a curve.

## 3. Data section
**D-06 A lone Ctrl-Z (0x1A) line at the end.** Observed: 7 files, for example `4200341369_DEVON_ULS_5_35_1_MainPass.las` line 90450 is a single character 0x1A (DOS end-of-file marker). Rule: a data line consisting only of 0x1A is the end of the data — stop there, add an info entry; it is not a value and not a row. Test: data followed by 0x1A gives the same rows as without it.

**D-07 Text that stands in for a number.** Observed: `1.#INF` (`4200342764_UNIV_42_1_ECS_Playback.las` line 9575), `-1.#IND` (`4238338546_University_2505_3HM_.las`, lines 3481 and 6028 among others), `(null)` ×167 (`4246137956_UNIV_NG_5021H_5INCH_HORIZONTAL.las`, line 126), `********` (Fortran overflow, `4200340740PnrUniv7-23_1.las` lines 4970 and 5253). Rule: a token that is not a number becomes `NaN`, counted per file and per curve in the report — the row stays and the other curves keep their values. Test: each of these four tokens in a row gives `NaN` for that cell only.

**D-08 Damaged line.** Observed: `4200340740PnrUniv7-23_1.las` line 10508 is a run of NUL bytes (with a 0x1A inside) instead of a data row; the scan counted it as one token. Rule: a line that cannot be split into the expected number of numeric values is reported with its line number; it is not turned into a row of invented values. Whether to skip such a line or turn it into an all-NaN row is decided with the depth rule in part 2 (an all-NaN row has no depth). Test: a line of NULs in the middle of data does not stop the load and is reported.

**D-09 Rows with the wrong number of values.** Observed: `4246135949_MAIN.las` has 17307 rows of 29 values and 3054 rows of 28, starting at line 8247 (the last value of the row is missing); `4200340123MAIN.las` ends with one row of 12 values (23 expected). Also 6 files have more values per row than curves in the header (24 vs 23, 34 vs 33, 20 vs 19, 88 vs 82, 39 vs 37) — the cause is not proven for each (D-05 explains the first). Rule: a row with fewer values than curves keeps its depth and the missing curves become `NaN`, with a warning that gives the line number and counts — the file is not rejected; a row with more values than curves is reported, and the extra values are not used. Proposed, to be confirmed by the owner. Test: short row → trailing `NaN`; long row → warning.

**D-10 WRAP = YES.** Observed: `4200340125Univ_7_8_1.LAS` (25 curves) writes the depth alone on one line, then lines of 6 values (1, 6, 6, 6, 6 values). The biggest wrapped file, `4200345990_20140426_LAS(masmp).LAS`, has 125 curve lines in its `~C` block (counted this round, `DEPT` first) and every data row has 125 values: the depth alone on one line, then lines of 6 (checked on lines 187–196). The first scan counted 123 because two curve lines start with a dot — `.DT57.USEC/FT` and `.MAS57.USEC/FT` — so there is no mnemonic before the first `.` and a strict `MNEM.UNIT` pattern skips them (the same mistake as D-05; this is the likely cause of the 123, inferred, the first scan was not re-run). Read with the rules below, the file gives 125 columns and 79,033 rows, depth 85.0 to 7988.2 with a smallest step of 0.1000 (run on commit `8653341`); that matches the header (`STRT` 85.0, `STOP` 7988.2, `STEP` 0.1): (7988.2 − 85.0) / 0.1 + 1 = 79,033. The two dotted lines are kept as curves in their column positions but get an empty mnemonic and the unit `DT57.USEC/FT` / `MAS57.USEC/FT`; their names are not recovered (not needed for the MUST features, left as it is). Rule: when WRAP is YES, read values until one row has as many values as there are curves, then start the next row; never assume a fixed number of values per line. Test: wrapped sample gives the same table as the unwrapped version of the same data; a header line that starts with `.` still counts as a curve (this last test is not written yet — to add with the next parser test).

**D-11 LAS 3.0 and repeated sections.** Observed: the 11 LAS 3.0 files have extra sections after the data (`~Lithology_Data`, `~Comment_Definition`, `~TracePresentation…`); `s_1e95aa3fbeb17f98a969ce83d5962c1c.las` has `~Parameter`, `~Curve` and `~Ascii` twice. Rule (scope says 3.0 is best-effort): read the first `~A…` or `~Log_Data` section only, ignore sections that do not start the data, and add an info entry that other sections were skipped. Test: a 3.0 sample with a lithology section still loads its log data.

**D-12 The header can lie about WRAP.** Observed: `4200340122MAINCOR.las` says `WRAP. NO` but its 26 curves are spread over 6 lines per row (line shapes: 6 values ×82580 lines and 1 value ×41290 lines). Its first rows at lines 175–181 show a depth, then lines starting with `-999.25`. Rule: decide the layout from the data, not only from the header: count the values on each line of the first rows; if the lines hold fewer values than curves, read as wrapped (a stream of values, `ncurves` per row) and add a warning that the header disagrees. Test: wrapped data with `WRAP. NO` still gives complete rows.

**D-22 Comment lines inside the data section.** Observed: `4200345990_20140426_LAS(masmp).LAS` has `~A` on line 165, then 21 lines that start with `#` (lines 166–186) listing the curve names six per line (line 183 is `#  SGRSFAC1    SGRSLTIM    SGRSQUAL     SGRTAF      SGRUAF        SP`); the numbers start on line 187. Without a rule for them (commit `7f06cb4`, run this round) the legend was read as values: 128 issues, first and last depth −999.25 and a smallest depth step of −2099.25, so the whole table was shifted; the row count (79,033) looked right, only the depth column gave it away (the mechanism is inferred from these symptoms). With the rule (commit `8653341`, run this round): 1 issue (22 values equal to −999, see D-16), depth 85.0 to 7988.2, smallest step 0.1000. The earlier figure "127 issues" was taken before the −999 warning existed. Rule: a data line whose first non-blank character is `#` is a comment — skip it, in the wrapped and the unwrapped layout alike; it is not a value and not a row, so no report entry is written for it (open question for the owner: count skipped comment lines in the report?). Test: `#` lines before, between and inside a wrapped row do not change the table (two tests in `LasDataParserTests`).

## 4. Depth
**D-13 Depth units are all feet, written four ways.** Observed: the first curve is `DEPT` or `DEPTH`/`Depth`, with unit `F` (88 files), `FT` (86+5), `ft` (7+5+2) or `Ft` (10); the STRT/STOP/STEP lines use the same four spellings. No file labels its depth as metres. Rule: depth is the first column; compare its unit case-insensitively; `F`, `FT` = feet; a metres label (`M`) would be converted to feet with a report entry — there is no such file here, so this rule comes from the spec only and gets a small test. Test: `F`, `FT`, `ft`, `Ft` all mean feet; `M` converts. Result (T9 code, all 203 files run): every file's depth is in feet, so nothing was converted; the metres rule is covered by a unit test only.

**D-14 Depth order.** Observed (non-wrapped files, from the scan): 161 ascending, 25 descending (example `4246135332_repeattwo.las`), 3 neither; 14 wrapped files were not checked. Two of the three "neither" are real: `4200343170_STATE_AQ_8_RUN2.las` jumps back at line 4464 (7763.5 → 7664.0) and then runs downwards from about line 8614; `s_1e95aa3fbeb17f98a969ce83d5962c1c.las` drops at line 20510 (10194.0 → 24.5) where its second `~Ascii` section starts (D-11). The third, `MAINCOR`, only looks mixed because it is wrapped (D-12). The first scan's duplicate figures (including 518 in `MAINCOR`) were wrong for that reason. Result (T8 code, all 203 files run, wrapped files included): 27 files are descending and were reversed (the first scan counted 25 among the non-wrapped files); 1 file needed a sort, `4200343170_STATE_AQ_8_RUN2.las` (518 rows moved), and it is also the only file with duplicate depths (200 rows dropped, first kept; I did not look into why they repeat); no file has a gap larger than 1.5 x its step; after the rules every file is strictly ascending. Rule: all descending → reverse the rows as a block; otherwise (jumps) → stable sort by depth, never reorder values inside a row, report how many rows moved; duplicates: first kept, counted (F3). Test: descending, jump-back and duplicate samples.

**D-15 STEP in the header is not reliable.** Observed: header STEP and the most common real step were compared in 189 files and differ in 3 (`4200340125MAIN.las` header 0.75, real 0.5; `4200342472_UNIV_9_31_1_LAS.las` header 0.25, real 0.5; the third is MAINCOR, an artifact). Rule: report both; use the real step for gap detection; never resample (scope). Test: a file whose STEP is wrong reports both numbers. Result (T8 code, all 203 files run): exactly the two files named above differ; the third of the first scan (`MAINCOR`) does not, as expected.

## 5. Missing-value markers
**D-16 Files use other markers besides the declared NULL.** Observed (all 203 files run this round, commit `8653341`, Core built Debug): 28 files contain at least one marker the header does not declare. By marker (files / values set to NaN): `-999.25` 2 / 23680 (`4238336177MAIN.las` and `4238336177_MAIN.las`, 11840 each, both declare NULL 0); `-999` 5 / 7967 (largest `4200341177_DRONE_BEE_1_MSIP_UBI_SPLICE_009.las`, 7905); `-9999` 2 / 12005 (`Oxy_USA_University_McFarland_8_Unit_1H_ThruBit_PnS.las` 11605, `4238338546_University_2505_3HM_.las` 400); `-99999` 0 / 0 (in the list, not seen in this data); `-9999.9999` 18 / 1918 (largest `s_7eec8ccf38a0378c41a61b611c4bf6d6.las`, 1836); `-9999.999` 1 / 9981 (`s_f729e898a62aed00d0e7de2a8d2ed241.las`, all in one curve). A search of the raw text for the literal tokens finds the same 18 files for `-9999.9999` and the same 1 file for `-9999.999`, and no file with the token `-10000`. The first scan counted 11 files for `-9999.9999` and 4 for `-999`; the loader finds 18 and 5 (the difference was not investigated; the newer figures are the ones checked against the raw text). Values such as `-270.1804` repeat only 3 times in one file, so they are real readings: "any value below -90" is **not** a valid rule. Rule (marker list approved by the owner): always apply the declared NULL (except 0, D-04) **and** a short fixed list of seven known markers `-999.25, -999, -9999, -99999, -9999.9999, -9999.999, -999.2`, matched as numbers and never by range. Only curve columns are changed; the depth column is never touched. Values are compared after conversion to `float`, the way they are stored: every spelling of a number meets in one bucket (`-999.2500`, `-999.250`), `-9999.9999` (stored as `-10000.0`, so a 1e-6 tolerance would miss it) is still found, and `-9999.999` stays a separate bucket. A value equal to the declared NULL is counted as declared and never again as a marker. Counts are kept per curve and per marker. Reporting policy: using the declared NULL is a note (routine, nearly every file); NULL = 0 not applied, no NULL declared, and every undeclared marker are warnings that show in the load report. Test: each of the seven markers → `NaN`; `-9999.9999` and `-9999.999` are both found and counted separately; `-270.1804`, `-60.112` and `0.0` stay; NULL 0 leaves zeros and still clears `-999.25`; depth is untouched; a declared NULL that equals a marker is counted once (`MissingValuesTests`). Seventh marker `-999.2` (found by the end-to-end check, T16: the GR curve chosen for a mud log had a median of -999.2): `4200343170_STATE_AQ_8_MUDLOG.las` declares NULL as `-999.25` but writes `-999.2` — `-999.25` cut short — in three curves (`GAMMA` 10,781 values, `10FTRATE` 9,703, `5FTRATE` 8,626; 29,110 in all, about 10,800 of its rows) and nowhere else in `data/` (counted over all 203 files, run on the code with the seventh marker: 1 file, 29,110 values; the other six markers give the same counts as above). It is a different number from the declared NULL, so the declared-NULL rule did not catch it. Like `-9999.999`, it rests on one file, so the owner approved it as a marker and it can be dropped if it proves too narrow. With it, the `GAMMA` curve of that file is all NaN, is passed over ("no valid values") and the plot says "No gamma ray curve" instead of showing an empty track under a legend. After the change 29 files (was 28) contain an undeclared marker. Test: `-999.2` → `NaN` and counted apart from a declared `-999.25` (`MissingValuesTests`). No file in `data/` lacks a NULL line, so that warning is covered by a unit test only.

## 6. Curves and units
Method: each curve was found by mnemonic, then its values were looked at (non-wrapped files with consistent rows, markers excluded) to see what the unit label really means. "Median" below = median over curves of each curve's own median.

**D-17 Neutron porosity: the unit label is not enough, and the old assumption was wrong.** Observed: `NPHI`, `TNPH` and `NPOR` are labelled `CFCF` on 124 curves (median 0.159, none with a median above 1) — these are fractions, not counts. `PERC` (49 curves, median 18.6), `PU` (8, 13.5) and `%` (5, 15.0) are percent. `V/V` (33, 0.161), `FRAC` (6, 0.226) and `DECP` (7, 0.265) are fractions. `CNLSC` with unit `CPS` (10 curves, median 333) is a count rate, **not** porosity. Rule: choose the neutron-porosity curve by mnemonic **and** unit class — percent (`PERC`, `PU`, `%`) → divide by 100; fraction (`V/V`, `FRAC`, `DECP`, `CFCF`) → keep; counts (`CPS`) → never chosen. As a safety net, warn when a "fraction" curve has a median above 1. Proposed; the `CFCF` decision rests on the values above, so confirm. Test: 25 % → 0.25; `CFCF` curve of 0.18 kept; `CPS` curve ignored. Result (T9 code, all 203 files run): unit labels differ in case (`pu`, `perc`, `Deci`, `cps`), so units are compared ignoring case. Two labels were not in the list above and are read as fractions: `Deci` (`NPHI`, 2 files: median 0.187, range -0.018 to 1.041) and `ft3/ft3` (`TNPH`, 1 file: median 0.211, range 0.005 to 1.873) — the values confirm it. Percent curves divided by 100 in 10 files; `CNLSC` with `CPS` was rejected 11 times; the median-above-1 safety net raised no warning; 129 files have no usable neutron curve. Correction found by looking at the plot (not by the numbers): in `39399.LAS` (wrapped, so outside the non-wrapped files measured above) the chosen `NPHI` is labelled `%` but its values are fractions (raw median 0.104, range -0.015 to 1.323), and dividing by 100 flattened it to about 0. The same file also has `NPOR` and `TNPH` labelled `CFCF`. Of the 10 percent-labelled neutron curves chosen, 9 have a raw median of 10.9 to 19.6 (real percent, divided) and this one is a fraction. Rule added, the mirror of the safety net above: a curve labelled percent whose median is below 1 is read as a fraction, is not divided, and gets a warning. Proposed, from one file, so the owner should confirm; the unit label alone is not trusted for neutron porosity.

**D-18 Bulk density.** Observed: units are `G/C3` (78), `G/CC` (10), `G/CM3` (2), `K/M3` (1 file); mnemonics are `RHOZ` (45 files), `RHO8` (32), `DEN` (26), `RHOB` (19). `DPHI` also matches "density" names but is a porosity — it must not be a density alias. Rule: aliases live in `CurveRules.cs`; the three g/cc spellings are equal, `K/M3` is divided by 1000 with a report entry. Test: each unit; `DPHI` is not chosen as RHOB. Result (T9 code, all 203 files run): a density curve was chosen in 90 files (`RHOZ` 45, `DEN` 26, `RHOB` 19); the `K/M3` file was divided by 1000; 113 files have none. Priority order: `RHOB`, `RHOZ`, `RHO8`, `DEN`.

**D-19 Gamma ray.** Observed: `GR` (100 files), `GR_EDTC` (43), `HGR` (42), `GRGC` (29), `GRAN` (19), `GRSG` (17), `GAMMA` (17); unit `GAPI` (131 curves), `API` (8). Rule: all of these units mean the same; when a well has several gamma candidates, take the first in the alias priority order and list the others in the report (F5). Test: two candidates → one chosen, the other reported. Correction (T9 code, all 203 files run): `GRAN` is labelled `%` or `perc` (19 curves), not `GAPI`, so it is not a gamma ray in API units and is not an alias; `GRTH` and `GRUR` are `PPM` (thorium, uranium) and are not aliases either. The first run found 38 files without a gamma curve; adding `SGR`, `CGR`, `GRTO`, `GRKT`, `GRGM`, `GRS`, `HSGR` and `HCGR` at the lowest priority brought it to 24. All the files that were still without one were listed with every curve whose name, unit or description mentions gamma: they are mud logs, cement bond logs or files with a few curves, and the only gamma-like curves left are `GR_1 (API)`, `GR_CAL (gAPI)` and `GGRM`/`GMSG (GAPI)` (one file each, meaning not certain, not added) and `GR (aapi)` (a misspelt unit, not accepted so as not to tune to one file). Rejected for the unit: `Gamma (u)` and `GR (aapi)` in one file each. A candidate whose values are all NaN is skipped for the next one (5 `GAMMA` curves).

**D-20 Resistivity.** Observed: many names — `RT_HRLT` (40 files), `DSLL`/`DDLL` (30 each), `LLD`/`LLS` (8), `RILD` (6), `MSFL` (6); unit `OHMM`, but also `OHM-M` (5 curves among the names listed) and an empty unit (`RLLD`, `RLLS`). Rule: `OHMM` and `OHM-M` are equal; an empty unit is accepted with a report entry; the deep curve is preferred over shallow/micro curves in the alias order. Test: `OHM-M` accepted, empty unit accepted with a note. Result (T9 code, all 203 files run): a resistivity curve was chosen in 96 files (`RT_HRLT` 40, `DDLL` 30, `RD` 6, `RILD` 6, `LLD` 7, `RLLD` with an empty unit 2); 107 files have none. The medium curves of the same logs (`RM_HRLT`, `RMLL`) and mud resistivity (`RMUD`) are not aliases.

**D-21 Out-of-scale values exist in real data.** Observed (excluding markers): density from -60.112 (`G/CC`) to 4.629 (`G/C3`), gamma ray up to 711.95, neutron `PERC` up to 524, neutron `V/V` up to 1.79. Rule: these values are never changed or removed (no silent edits); the plot uses fixed standard scales and lets off-scale values run off the track; markers are a later feature (F10). Test: a density of -60 stays in the data and the plot call does not throw.

**D-23 A chosen curve can have values that cannot be what its name says.** Observed (end-to-end check, T16, all 203 files run): after the structural checks (ascending depth, no marker left, no Infinity, equal lengths) pass for every file, looking at the median of each chosen curve finds two more cases. `4246135949_MAIN.las`: density `DEN` (`G/C3`) has a median of 0.189 g/cc (range -0.016 to 1.483), far below any rock; in the same file the other `G/C3` curve, `DCOR`, holds values near 2.6 and a `V/V` curve holds values near 250, so the data columns probably do not follow the order of the header (inferred from the values, not proven). `4246138787_UNIV_4_29_2_Mudlog.las`: the `GAMMA` (`GAPI`) curve of a mud log has a median of 0 (a surface mud log, not a wireline gamma ray). Every other chosen gamma ray (179 files) and density (90 files) has a median inside the ranges below. Rule: for gamma ray and bulk density, compare the median of the chosen curve (after any unit conversion) with a wide usual range — gamma ray 1 to 500 GAPI, density 1.0 to 3.6 g/cc — and add a warning when it falls outside; the values are not changed and the curve is still chosen and drawn. The ranges are general physical limits, chosen wide so that only an impossible curve is caught; they are my own estimate, not checked with a petrophysicist.
